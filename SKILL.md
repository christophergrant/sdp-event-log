# SDP event-log queries

Start with the [Databricks event-log examples](https://docs.databricks.com/aws/en/ldp/monitor-event-logs) and [pipeline events table reference](https://docs.databricks.com/aws/en/admin/system-tables/pipeline-events). They cover errors, flow metrics, expectations, Auto Loader operations, backlog, classic autoscaling, prior updates, runtime versions, lineage, and refresh planning. Write custom SQL only for a question those examples do not answer.

Resolve the user's starting point before querying metrics. Accept a pipeline ID or URL, exact pipeline name, pipeline update ID, Spark streaming `runId`, flow name, or fully qualified table name. Map it to `workspace_id` and `pipeline_id`, plus `update_id`, flow, or table when supplied; keep that scope through subsequent queries. An SDP “run ID” usually means the pipeline `update_id`, but Spark `progress_json.runId` and a Jobs run ID are different identifiers. Test the appropriate mapping instead of treating UUIDs as interchangeable. For name matches, show all candidate pipelines and their last-seen times; do not silently choose one. Use [identifier resolution](references/cross-pipeline.md#resolve-the-starting-identifier) for lookup SQL and [cross-pipeline delays](references/cross-pipeline.md) when tracing connected tables.

Prefer the current pipeline events system table for monitoring across pipelines. Its documented Beta path is `system.lakeflow_pipeline_events_preview.pipeline_events`; verify the path because GA is planned to move it. For the exact configuration used to start one update, use that pipeline's event log even when the system table is available: the preview system-table schema omits `details.create_update.config.configuration` and some other fields. Query the `create_update` event for the specific `update_id` through `event_log('<pipeline-id>')` as the pipeline's run-as user (usually its owner), or through a published event-log table with `SELECT` access. If TVF access is denied, an authorized caller can try the raw [Pipeline Events API](https://docs.databricks.com/api/pipelines/v2/events) filtered by `update_id`; verify that the response includes `details`. The generated `databricks pipelines list-pipeline-events` command can omit `details`, so use `databricks api get` for this check. For Unity Catalog legacy publishing mode, the TVF requires the pipeline owner and a SQL warehouse or shared cluster. See [event-log access](https://docs.databricks.com/aws/en/ldp/monitor-event-logs) and [legacy-mode access](https://docs.databricks.com/aws/en/ldp/live-schema). For legacy Hive metastore pipelines, the configured pipeline storage location can contain `system/events`; check access and whether multiple pipelines share it. The per-pipeline source uses `timestamp`; the system table uses `event_time` and top-level workspace, pipeline, and update IDs.

Before interpreting results:

- Scope the query to the requested workspace or account, pipeline, and time window. Keep identifying columns in the result when the scope spans pipelines or updates.
- Inspect representative `event_type`, `details`, `origin`, and `maturity_level` rows. Payloads vary by type; `EVOLVING` fields can change. Use the [schema reference](https://docs.databricks.com/aws/en/ldp/monitor-event-log-schema) for field meaning.
- Join update events by workspace, pipeline, and update IDs; aggregate timeline periods first if the answer needs one row per update. Select the latest SCD2 row from `system.lakeflow.pipelines` for current metadata.
- Treat missing measurements as unknown. `cluster_resources` and `autoscale` cover classic compute; backlog depends on source and runtime. `stream_progress` omits built-in input and processed row rates.
- For rates from `observedMetrics`, use an explicitly named, verified per-batch metric and a nonzero duration. Never call the first map value “rows processed.”

## Primary questions

- **Is `<pipeline>` running, and when did each flow last finish a batch?** Check the latest `update_progress` state and the last `stream_progress` event for every event-visible flow. Use the [all-flows pattern](references/query-patterns.md#time-since-the-last-completed-batch). A quiet source or delayed event delivery is not proof of a stall.
- **For `<flow>`, is backlog accumulating, steady, or recovering?** Use the [backlog-trend pattern](references/query-patterns.md#backlog-trend-and-return-to-baseline). Compare end-of-batch readings with a healthy baseline for the same source; a continuous stream need not reach zero. For an append-only Delta source, corroborate the trend with [source arrival versus consumer advance rates](references/cross-pipeline.md#compare-source-arrivals-with-consumer-advance). Estimate time back to baseline only after a sustained decline.
- **Which settings actually started this pipeline update?** Find its `create_update` row in the per-pipeline log, matching `origin.update_id`; inspect `details:create_update.config.configuration` and other relevant `config` fields. The system table omits the configuration map. Check `runtime_details` separately for runtime settings.
- **What is the end-to-end latency of `<flow>`?** Define the source and output timestamps first. Record-level latency needs an original event timestamp or ID carried to the output and a final processing or publication time. If those are unavailable, report the narrower, tested table commit-to-output commit handoff and stage batch durations using [cross-pipeline delays](references/cross-pipeline.md); label the endpoints explicitly. A lineage timestamp or Spark watermark is not end-to-end latency.
- **What changed between the last healthy update and this one?** Establish a baseline update from observed health, not merely the preceding ID. Compare the same flow under similar load and equal observation windows with the [two-update pattern](references/query-patterns.md#compare-two-update-windows). Diff start configuration from the per-pipeline log and inspect `user_action` separately. Report the changes and their times; a correlation is not proof of cause. Use `DESCRIBE HISTORY` for Delta commit size or file actions.

## Further diagnostics

- **What happened in a prior run after it vanished from the UI?** Use the [previous-updates example](https://docs.databricks.com/aws/en/ldp/monitor-event-logs#monitor-pipeline-updates-by-querying-previous-updates) to find the `update_id`, then query retained events. Spark GC pauses and executor failures need Spark or driver logs.
- **Where did a long batch or initialization spend time?** Compare `update_progress` states, [Auto Loader `operation_progress`](https://docs.databricks.com/aws/en/ldp/monitor-event-logs#monitor-cloud-file-ingestion-with-auto-loader) listing/backfill events, and `stream_progress.progress_json.durationMs`. Use the Spark UI, query profile, or logs for task-level cause.
- **Why did classic compute scale despite low CPU, or scale down while behind?** Read task-slot utilization, queued tasks, executor count, `autoscale_info`, and `autoscale` requests together. See the [classic resource example](https://docs.databricks.com/aws/en/ldp/monitor-event-logs#monitor-compute-resource-utilization-for-classic-compute) and [field pattern](references/query-patterns.md#classic-autoscaling-evidence).
- **Were file notifications delayed or did processing pause?** Event-log operation, flow, and batch events show processing activity; Azure Event Grid delivery timing needs Event Grid metrics or `cloud_files_state` where available.

For the custom calculations and the backlog/executor or named observed-metric queries, read [query-patterns.md](references/query-patterns.md). Explain the measurement and its limits alongside the SQL.
